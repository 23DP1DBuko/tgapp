Critical Issue — Transaction queries not using  transaction.get() :
The most serious bug is in all 3 functions that use transactions ( joinGiveaway ,  completeGiveawayTask ,  drawGiveawayAdmin ). They call  db.collection(...).where(...).get()  inside a  runTransaction  callback instead of using  transaction.get() . In the Firebase Admin SDK,  transaction.get()  only accepts  DocumentReference  objects, not  Query  objects. So these:
// js
const existingEntries = await db.collection(...).where(...).get()
are NOT part of the transaction — they're standalone reads. This means:
1. For  joinGiveaway : A race condition exists where duplicate entries can be created
2. For  completeGiveawayTask : Stale  completedTaskIds  can be read
3. For  drawGiveawayAdmin : Entries are read outside the transaction, so the draw may be inconsistent
The fix: Move queries outside the transaction (for the entries check), or use a deterministic document ID like  ${telegramUserId}  so you can read with  transaction.get(entryDocRef) .
Other issues:
-  getGiveawayEntries  uses  .orderBy('totalTickets', 'desc')  — this requires a composite index on  giveaways/{id}/entries  with  totalTickets DESC . Needs to be added to  firestore.indexes.json .
-  drawGiveawayAdmin  uses  Math.random()  for weighted lottery — acceptable for a streetwear store but not cryptographically fair. Fine for this use case.
-  completeGiveawayTask  updates  totalTickets  via  currentTickets + ticketsGranted  instead of  FieldValue.increment() . Since the read happens outside the transaction (see above bug), there's a race. If you move the read inside the transaction using a deterministic doc ID, then the non-increment approach works. Otherwise use  FieldValue.increment() .
-  verificationResult.user.username  is accessed but the  TelegramInitDataUser  type only has  id?: number . The  username  field comes through at runtime but TypeScript won't know about it. Should add  username?: string  to the type or use type assertion.
Critical — Transaction reads use  db.collection(...).get()  instead of  transaction.get() :
In  joinGiveaway ,  completeGiveawayTask , and  drawGiveawayAdmin , the code does this inside  runTransaction :
// ts
const existingEntries = await db.collection(...).where(...).get()
This is not a transactional read — it bypasses the transaction and reads directly from Firestore. The Admin SDK's  transaction.get()  only accepts  DocumentReference , not  Query , so queries can't participate in transactions. This causes two bugs:
1.  joinGiveaway : Two users can race and both get no existing entries → duplicate entries created
2.  completeGiveawayTask : The  completedTaskIds  read may be stale
3.  drawGiveawayAdmin : Entries are read outside the transaction, so a concurrent task completion could skew the draw
Fix: For  joinGiveaway  and  completeGiveawayTask , move the entries query before the transaction. For the entries subcollection, use a deterministic document ID like the stringified  telegramUserId  so you can do  transaction.get(entryDocRef)  and get atomic reads.
 getGiveawayEntries  needs a composite index —  orderBy('totalTickets', 'desc')  on the  entries  subcollection requires an index. Add to  firestore.indexes.json .
 completeGiveawayTask  race on  totalTickets  — Since the entry doc isn't read atomically,  currentTickets + ticketsGranted  can be wrong. Use  FieldValue.increment(ticketsGranted)  instead.
 TelegramInitDataUser  missing  username  — The code accesses  verificationResult.user.username  but the type only has  id?: number . Add  username?: string  to the type in helpers.ts, or use a type assertion.
Style matches existing code well. The weighted draw algorithm is correct for a streetwear giveaways app.`
