# YungWear — Структура Giveaway (Розыгрыши)

Документ описывает архитектуру и логику giveaway-системы для Mini App. Это план для дизайна + модели данных + механик, не финальный код.

---

## 1. Типы giveaway

Giveaway всегда строится вокруг **набора призов**, а не количества "победителей" как отдельного параметра. Количество победителей = количество призовых мест = количество товаров, добавленных в giveaway.

### Тип A — Один приз, один победитель
- Админ выбирает 1 товар из каталога (продукт из базы продуктов).
- Автоматически: `winnersCount = 1`.
- Простой режим — один слот на "1 место".

### Тип B — Несколько призов, несколько победителей, с рейтингом мест
- Админ выбирает N товаров.
- Каждому товару присваивается **место** (1st, 2nd, 3rd...) в порядке добавления или вручную через drag-and-drop в админке.
- `winnersCount = N`, где N = количество выбранных товаров.
- Место **не влияет на количество билетов**, необходимых для выигрыша — это отдельная механика (см. ниже, п.4). Место просто определяет, какой приз получает какой по счёту победитель при розыгрыше.

**Важно:** ранг приза (1st/2nd/3rd) используется только для:
1. Отображения в UI (какой приз "круче").
2. Порядка розыгрыша (сначала разыгрывается 1 место, потом 2-е и т.д., либо наоборот — решается на этапе дизайна).

Ранг **не даёт** более высокие шансы обязательно тем же людям — правило "как выпало, так выпало" (равновероятный выбор среди всех билетов, независимо для каждого призового места, без повторного участия одного и того же победителя в нескольких местах одного giveaway).

## 2. Жизненный цикл giveaway (статусы)

```
draft → scheduled → live → ending → finished → announced
```

- **draft** — админ создаёт, но не публикует.
- **scheduled** — опубликован, но старт в будущем (опционально).
- **live** — открыт для участия, таймер идёт.
- **ending** — последние N минут (можно использовать для UI-эффекта "заканчивается скоро").
- **finished** — таймер истёк, розыгрыш произведён (список победителей определён).
- **announced** — победителям отправлены сообщения в Telegram, результат опубликован.

## 3. Модель данных (Firestore)

### Коллекция `giveaways`

```
giveaways/{giveawayId}
  title: string
  description: string
  status: 'draft' | 'scheduled' | 'live' | 'finished' | 'announced'
  startAt: Timestamp | null
  endAt: Timestamp
  prizes: [
    {
      productId: string        // ссылка на продукт из каталога
      place: number             // 1 = первое место, 2 = второе и т.д.
    }
  ]
  winnersCount: number          // = prizes.length, вычисляется автоматически
  accessLevel: 'public' | 'early_access_only'  // см. п.6
  entryTasks: [
    {
      id: string
      type: 'join_channel' | 'invite_friend' | 'like_product' | 'custom'
      label: string              // "Подписаться на канал"
      ticketsGranted: number     // сколько билетов даёт выполнение
      verifyMethod: 'telegram_api' | 'referral_count' | 'manual'
    }
  ]
  baseEntryTickets: number       // билетов за простое присоединение (обычно 1)
  createdAt: Timestamp
  finishedAt: Timestamp | null
  winners: [
    {
      place: number
      productId: string
      telegramUserId: number
      ticketsAtWinTime: number
    }
  ] | null
```

### Коллекция `giveawayEntries` (или подколлекция внутри giveaway)

```
giveaways/{giveawayId}/entries/{telegramUserId}
  telegramUserId: number
  telegramUsername: string | null
  joinedAt: Timestamp
  completedTasks: string[]        // список id из entryTasks, которые выполнены
  totalTickets: number            // baseEntryTickets + сумма ticketsGranted по completedTasks
```

Хранить `totalTickets` денормализовано (пересчитывать при каждом завершении задания) — это позволяет быстро строить лидерборд без агрегаций на клиенте.

## 4. Механика билетов / шансов

- Присоединение к giveaway = `baseEntryTickets` (обычно 1 билет).
- Каждое доп. действие (подписка на канал, пригласить друга, и т.д.) добавляет фиксированное количество билетов, заданное в `entryTasks[].ticketsGranted`.
- Пригласить друга может масштабироваться (например, +1 билет за каждого приглашённого, а не разово) — это отдельный тип задания `invite_friend` с логикой "начисляется за каждое успешное действие", а не разово как `join_channel`.
- Итоговый шанс пользователя = `totalTickets` / `сумма totalTickets всех участников`.

### Механизм розыгрыша (backend, Cloud Function по таймеру или триггеру)
1. Собрать всех участников с `totalTickets > 0`.
2. Построить "весовой пул" — каждый билет = один шанс (по сути, взвешенный случайный выбор).
3. Для каждого призового места (по порядку от 1-го до последнего):
   - Выбрать одного победителя взвешенно случайно.
   - Убрать выбранного пользователя из пула (чтобы один человек не выиграл два приза в одном giveaway — если это правило устраивает, иначе можно разрешить).
4. Записать результат в `winners[]`.
5. Перевести giveaway в статус `finished`.

## 5. UI / UX структура

### Экран списка giveaway
- Карточка активного giveaway: обложка приза (или коллаж призов, если несколько), таймер до конца, количество участников.
- Статус-бейдж: "Live", "Скоро", "Завершён".

### Экран одного giveaway
1. **Хедер** — название, таймер (обратный отсчёт), картинка главного приза (1 место).
2. **Список призов** — если призов несколько, показать все места (1st/2nd/3rd) с картинками товаров.
3. **Кнопка "Присоединиться"** — создаёт запись в `entries`, даёт `baseEntryTickets`.
4. **Секция "Увеличить шансы"** — список заданий из `entryTasks`, каждое с чекбоксом/статусом выполнено/не выполнено и количеством билетов, которое оно даёт.
5. **Отображение текущих шансов** — "У тебя N билетов из M — шанс X%" (обновляется после каждого выполненного задания).
6. **Один из двух режимов визуализации соперничества (выбрать один на дизайн-этапе):**
   - **Лидерборд** — топ участников по билетам (без раскрытия точных шансов остальных, если не нужно).
   - **Колесо/рулетка** — визуальный элемент в момент розыгрыша (анимация выбора победителя), не обязательно показывающий реальные веса, скорее эффект "момента развязки".

   Рекомендация: **лидерборд во время live-фазы** (мотивирует выполнять задания, соревновательный эффект) + **колесо/анимация только в момент объявления результата** (эмоциональный момент, не техническая механика). Это комбинирует оба твоих варианта без конфликта.

### Экран результата
- После `finished/announced`: показать список победителей по местам, с аватарками/username (если публично) или просто "Победитель определён, проверьте личные сообщения" (если приватно).
- Автоматическая отправка сообщения в Telegram каждому победителю (через бота) с указанием приза и инструкцией, что делать дальше (например, подтвердить получение, указать адрес).

## 6. Early Access / эксклюзивные giveaway

- Поле `accessLevel: 'public' | 'early_access_only'`.
- `early_access_only` giveaway видны и доступны только пользователям, которые соответствуют критерию (например, `rewardTier >= 2` из системы Rewards, или отдельный флаг `hasEarlyAccess: true` на пользователе).
- В общем списке giveaway такие розыгрыши либо скрыты полностью для обычных пользователей, либо показаны как заблокированные ("Доступно с уровня Gold — узнать как получить").
- Это напрямую связывает giveaway-систему с существующей Rewards/Referral механикой, вместо создания отдельной несвязанной системы доступа.

## 7. Админ-панель — что нужно для управления

- Создание giveaway: выбор товара(ов) из каталога, назначение мест (drag-and-drop порядок = место).
- Настройка `entryTasks` — набор доступных типов заданий с указанием, сколько билетов каждое даёт.
- Настройка `accessLevel`.
- Просмотр списка участников и их билетов в реальном времени (для live giveaway).
- Кнопка "Завершить сейчас" (ручной запуск розыгрыша до истечения таймера, на случай форс-мажора).
- После розыгрыша — просмотр победителей, кнопка "Отправить уведомления" (если не выполнено ��втоматически), возможность вручную переопределить победителя в редких случаях (спор/бан за читерство).

## 8. Защита от накруток (важно, не пропустить)

- Задание "Подписаться на канал" должно проверяться через Telegram Bot API (`getChatMember`), а не просто верить клику пользователя.
- Задание "Пригласить друга" должно засчитываться только если приглашённый — реальный новый пользователь (не повторный аккаунт), использовать существующую систему Referral для валидации.
- Ограничить одну запись `entries` на один `telegramUserId` — без дублирования аккаунтов на один и тот же giveaway.
- Логировать `completedTasks` с временными метками — на случай спора о читерстве нужна история.

## 9. Итоговая сводка механики

| Сценарий | winnersCount | Место влияет на билеты? | Кто получает какой приз |
|---|---|---|---|
| 1 товар | 1 | Нет | Единственный победитель получает единственный приз |
| N товаров | N | Нет | Каждое место разыгрывается отдельно, победитель каждого места определяется случайно по билетам, без гарантии что у победителя 1-го места было больше билетов |

**Ключевой принцип:** ранг приза — это ТОЛЬКО про то, какой товар "круче", а не про то, что нужно больше билетов для топ-приза. Шансы одинаково взвешены для всех мест; просто первое место разыгрывается первым (или по правилам дизайна).
